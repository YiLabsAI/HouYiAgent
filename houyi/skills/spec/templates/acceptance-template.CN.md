## 1. 实现任务拆解

### Sprint 划分原则

| 原则 | 含义 | 反模式 |
|------|------|--------|
| **纵向切片** | 每个 Sprint 交付 SDK → Server → UI 完整链路 | 先做完所有 SDK 再做 UI |
| **增量可用** | Sprint N 交付后产品多一项完整可用能力 | 做了一半等下个 Sprint |
| **依赖链驱动** | Sprint 边界由架构依赖链的自然断点决定 | 随意分配不考虑依赖 |
| **风险前置** | 高复杂度、核心架构模块优先 | 最难的留到最后 |

### 完成链定义（Definition of Done Chain）

```
Task ✅ ──→ Sprint ✅ ──→ Gate ✅ ──→ Phase ✅
 (做了)       (做全了)      (做对了)      (可交付了)
```

| 层级 | 标记条件 | 反模式 |
|------|---------|--------|
| **Task** ✅ | 代码 + 测试通过 + lint clean | 代码写完未跑测试 |
| **Sprint** ✅ | 该 Sprint 所有 Task ✅ | 有 Task ⬜ 就标完成 |
| **Gate** ✅ | 所有 MUST 条件验证且有证据 | Task 完成自动标 Gate |
| **Phase** ✅ | Gate 所有 MUST ✅ | "差不多了"就声称完成 |

传导规则：Task → Sprint → Gate → Phase，不可跳层。
**禁止虚标**：任何 ✅ 必须有可运行的验证证据，否则视为交付违规。

### 验证工作流（Sprint 交付 Checklist）

```
Step 1: 逐 Task 确认
  ├─ 代码实现？测试通过？lint clean？覆盖率达标？
  └─ 任何 Task 未达标 → 停止，修复后重新检查

Step 2: Sprint 状态
  ├─ 所有 Task ✅ → Sprint 标记 ✅
  └─ 有 Task ⬜ → Sprint 不得标 ✅

Step 3: Gate 逐条验证
  ├─ 每个 MUST 条件：关联 Task 全 ✅？
  ├─ 执行验证（测试 / 检查输出 / 审查行为）
  ├─ 填 Result 列（✅ 或 ❌）+ Evidence 列（测试文件 + case 数）
  └─ 有 MUST ❌ → 停止，修复后从 Step 1 重来

Step 4: Phase 交付声明
  ├─ 所有 MUST Gate ✅ → Phase 完成
  └─ 记录到交付日志
```

### 工程实践约束

| 维度 | 规则 | 反模式 |
|------|------|--------|
| 文件命名 | 源文件 `<module>.py`；测试 `test_<module>.py` 镜像 | `test_phase3_stuff.py` |
| 函数命名 | `test_<subject>_<behaviour>[_<condition>]` ≤ 35 字符 | 50 字符长名称 |
| 测试目录 | 与 `houyi/` 源目录结构完全镜像 | 扁平化 `tests/` |
| 测试覆盖 | 每非平凡模块 ≥ 4 case：happy + boundary + error + interaction | 全是 happy path |
| 公共 API | Docstring + type hints 必需 | 裸 `dict` / `Any` |
| 代码注释 | 英文，仅解释非显而易见的意图 | 中文注释或叙述性注释 |

### 复杂度评估

| 代号 | 含义 | 预估代码行 | Agent 交互轮次 |
|------|------|-----------|--------------|
| S | 单文件，逻辑清晰 | < 80 | 1–2 |
| M | 1–2 文件，中等设计决策 | 80–200 | 2–4 |
| L | 多文件，需集成测试 | 200–400 | 4–8 |
| XL | 核心架构，需性能验证 | 400+ | 8+ |

状态标记：⬜ 未开始 · 🔵 进行中 · ✅ 完成 · ⏸ 阻塞

### 两级测试验收标准

> 适用于所有 Phase Gate。定义一次，各 Gate 引用。

#### 第一级：通用质量关卡（所有 Phase 必须）

| # | 条件 | 验证方式 | 备注 |
|---|------|---------|------|
| Q-1 | `make check` 全量通过 | 退出码 0 | 含 ruff lint + format + complexity + mypy + tsc + pytest + vitest |
| Q-2 | 新增代码行覆盖率 ≥ 90% | `pytest-cov` 报告 | 核心模块 ≥ 95% |
| Q-3 | 集成测试 + E2E 测试通过 | `pytest -m integration` | 涉及真实 LLM 调用的测试可标记 `slow`，CI 可选跳过但本地必须验证 |

#### 第二级：Phase 业务验收（每个 Gate 定义）

每个 Gate 在其业务门中定义具体验收条件。格式见下方 Gate 模板。

**交付日志分区原则**：

| 类别 | 归属区域 | 编号规则 | 示例 |
|------|---------|---------|------|
| **Sprint 交付** | Sprint N 任务表 | S*-T* | S7-T1 ~ T6 |
| **Bug 修复** | "第 N 轮修复" 段落 | B*-xx ~ B*-yy | 第十轮修复（B3-58~B3-61） |
| **架构修正** | "Phase X.Y 架构修正" 表格 | F-* | F-4 ~ F-7 |

三者分区明确，不得混排。
